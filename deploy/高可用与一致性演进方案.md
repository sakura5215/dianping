# 高可用与一致性演进方案

> 本项目从「单机 Redis + 应用主动双删」演进到「Redis 主从+哨兵 + Canal 订阅 binlog 被动失效缓存」。

---

## 一、Redis 主从 + 哨兵

### 架构

```
                ┌─────────────┐
    写/读 ────▶ │  主节点 6379 │
                └──────┬──────┘
              ┌────────┼────────┐
          复制 ▼           复制 ▼
        ┌─────────┐    ┌─────────┐
        │ 从 6380 │    │ 从 6381 │
        └─────────┘    └─────────┘

    哨兵 26379 / 26380 / 26381（quorum=2，监控主节点，故障自动选主）
```

### 解决了什么

| 问题 | 手段 |
|---|---|
| 单点故障 | 主挂了，哨兵在 down-after-milliseconds（5s）后判定主观下线，达到 quorum（2 票）判定客观下线，自动把一个从节点提升为新主 |
| 读压力 | 主从复制 + 读写分离，读分摊到从节点 |
| 数据安全 | AOF + RDB 持久化，主从复制保多副本 |

### 关键配置

- 主从：`slaveof 127.0.0.1 6379`
- 哨兵：`sentinel monitor mymaster 127.0.0.1 6379 2`（quorum=2）
- `down-after-milliseconds 5000`（5 秒无响应判主观下线）

### 应用接入方式（两种）

1. **单机模式**（默认）：`REDIS_HOST:localhost REDIS_PORT:6379`
2. **哨兵模式**：设置环境变量走哨兵，应用不直连主节点，由哨兵告知当前主节点地址，主从切换对应用透明
   ```
   REDIS_SENTINEL_NODES=localhost:26379,localhost:26380,localhost:26381
   REDIS_SENTINEL_MASTER=mymaster
   ```

### 已验证

- 主 6379 + 从 6380/6381 复制正常（`connected_slaves:2`）
- 杀掉 6379 后，哨兵约 8s 内自动把 6380 提升为新主，6381 自动重定向到 6380
### 局限（面试要主动讲）

- 主从解决**读**扩展和**高可用**，但**不能解决写瓶颈**（写只能走主）
- 主从是**异步复制**，主挂的瞬间可能有少量数据没同步到从（复制延迟）
- 真要水平扩写，得上 **Redis Cluster**（数据分片到 16384 个 slot）

## 二、Canal 订阅 binlog 解决缓存一致性

### 背景：原方案的问题

原 update 走 Cache-Aside「双删」（应用主动删 Redis L2 + Caffeine L1）：

```java
updateById(shop);                              // 1. 更新 DB
stringRedisTemplate.delete(CACHE_SHOP_KEY + id); // 2. 删 Redis
shopLocalCache.invalidate(id);                 // 3. 删 Caffeine
```

问题：
1. **依赖业务代码记得删**——忘了删就脏读；
2. **删除动作和 DB 提交之间仍有窗口**——删缓存后、DB 提交前，别的请求回源读到旧数据又写回缓存；
3. **别的服务/脚本直接改库时，缓存不知道**——一致性完全失效。

### 新方案：Canal 订阅 binlog

```
 应用/脚本 ──UPDATE──▶ MySQL（写 binlog）
                          │
                     Canal 伪装成从库拉 binlog
                          │
                     Canal Server (11111)
                          │ 推送变更事件
                          ▼
               CanalCacheSyncListener（应用内）
                    解析 tb_shop 的 UPDATE/DELETE
                          │
              ┌───────────┴───────────┐
          失效 Redis L2           失效 Caffeine L1
```

核心思想：**把"主动双删"改成"被动监听 binlog 失效"**。无论谁改的库、怎么改的，binlog 都会记录，Canal 都能推过来，缓存据此失效，做到**最终一致**。

### 关键代码

`CanalCacheSyncListener`（`com.dianping.mq` 包）：

- `@PostConstruct` 启动守护线程，连 Canal Server（`localhost:11111`），订阅 `dianping.tb_shop`
- 收到 `ROWDATA` 类型、`UPDATE`/`DELETE` 事件的 `tb_shop` 变更，从 `beforeColumns` 里取 `id`
- 失效 `cache:shop:{id}`（Redis L2）+ `shopLocalCache.invalidate(id)`（Caffeine L1）
- 成功 `ack(batchId)`，失败 `rollback(batchId)` 重试（保证不丢消息）

### MySQL 前置条件（已满足）

```sql
-- 需开启 binlog（ROW 格式）
SHOW VARIABLES LIKE 'log_bin';        -- ON
SHOW VARIABLES LIKE 'binlog_format';  -- ROW
SHOW VARIABLES LIKE 'server_id';      -- 1（需唯一）

-- Canal 账号（有读 binlog 权限）
CREATE USER 'canal'@'%' IDENTIFIED BY 'canal123';
GRANT SELECT, REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'canal'@'%';
```

> ⚠️ **环境坑（已解决）**：本机 MySQL 的 `log-bin` 前缀原本是中文（`郭思成的机械革-bin`，安装时用中文系统名自动生成），Canal 容器内字符编码会把中文 binlog 文件名变成乱码，导致 `errno=1236`（找不到 binlog）。已把 `my.ini` 里 `log-bin="郭思成的机械革-bin"` 改成 `log-bin="mysql-bin"` 并重启 MySQL 服务，Canal 正常拉取 binlog。

### 已验证（端到端）

- `mvn compile` 通过（canal.client + canal.protocol 依赖正常）
- Canal Server 成功连 MySQL，`find start position successfully, journalName=mysql-bin.000001`
- 后端 `CanalCacheSyncListener` 启动并订阅 `dianping.tb_shop`
- **端到端**：`UPDATE tb_shop SET name=... WHERE id=1` → 后端日志输出 `[Canal] 检测到 tb_shop.id=1 变更，已失效多级缓存` → Redis `cache:shop:1` EXISTS 从 1 变 0，缓存被自动失效

### 一致性模型演进（面试讲清）

| 方案 | 一致性 | 特点 |
|---|---|---|
| 双删（原方案） | 最终一致，但有窗口 | 简单，依赖代码 |
| 延迟双删 | 最终一致，窗口更小 | 删两次 + sleep，sleep 时长难定 |
| **Canal 订阅 binlog（本方案）** | **最终一致，窗口可控** | 解耦、可靠、可扩展 |
| 强一致（读写锁/事务） | 强一致 | 性能差，电商读多写少场景不划算 |

### 已验证

- `mvn compile` 通过（canal.client + canal.protocol 依赖正常）
- Canal 镜像、启动脚本、配置就绪（`deploy/canal/`）

## 三、本地部署清单

| 组件 | 端口 | 启动方式 |
|---|---|---|
| Redis 主 | 6379 | `bash deploy/redis/start-all.sh`（含主从+哨兵） |
| Redis 从 | 6380/6381 | 同上 |
| Sentinel | 26379-26381 | 同上 |
| Canal Server | 11111 | `bash deploy/canal/start-canal.sh` |
| MySQL | 3306 | 已开 binlog + canal 账号 |

启动顺序：MySQL → Redis 集群 → Canal → 应用。

应用可通过环境变量切换单机/哨兵模式：
```bash
# 单机（默认）
export REDIS_HOST=localhost REDIS_PORT=6379

# 哨兵高可用
export REDIS_SENTINEL_NODES=localhost:26379,localhost:26380,localhost:26381
export REDIS_SENTINEL_MASTER=mymaster
```
